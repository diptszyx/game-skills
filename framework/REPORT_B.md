## Implementation and integration

Both services use the existing `IClock`, `Reward`, and `IRewardGrantor`. Public service mutations return `DailyResult` with `DailyError`. Invalid constructor configuration leaves an unusable service whose operations return `InvalidConfig`, without throwing. Configured templates and reward tables are copied into each service, including booster dictionaries. No mutable static state or additional package dependencies were introduced.

`DailyCheckInService.Claim()` sends `checkin:yyyy-MM-dd` to the grantor. The next slot advances only after Granted/AlreadyClaimed, wrapping across five slots; rejection can be retried. UTC date ordinal parity chooses one of two configured reward rows.

`DailyQuestsService.Refresh()` establishes or updates the active set. `RecordEvent()` and `Claim()` also refresh automatically. `Quests` returns a snapshot; reading it does not mutate state. Selection takes a circular window from the configured ordered templates, starting at date ordinal modulo template count. Weekly selection uses the containing Monday's week ordinal. Event validation and overflow preflight happen before reset or progress mutation. Any overflowing matching quest rejects the entire event, even when capping would otherwise hide the overflow.

Daily claim IDs are `quest:yyyy-MM-dd:<questId>`. Weekly claim IDs use the same format with the containing UTC Monday as the date. IDs must be unique across both template pools. Weekly progress/claimed flags survive daily resets within the same week and reset at Monday 00:00 UTC.

Persistence is explicit: call each module's `Save(document)` and then the existing SaveStore. Each module writes exactly one version-1 section (`dailyCheckIn`, `dailyQuests`) through WriteSection and restores through ReadSection. Version, dates, ranges, selected IDs, duplicate entries, and completion/claim consistency are validated. Corruption restores module defaults and returns `CorruptSection`. Missing sections restore defaults successfully. Backward clocks return `ClockReversed`; saved high-water dates prevent reopening earlier periods after a round trip.

## AMBIG decisions

- Section 7 fixes five slots and two alternating daily reward tables, but does not define the rotation anchor, slot advancement, missed-day handling, or how table rotation relates to slots. Simplest choice: date ordinal since 0001-01-01 modulo two selects the row; successful/reconciled claims advance the slot modulo five; missed days preserve the next slot while date-based table rotation continues. Two rows of five rewards are required in config.
- Quest selection algorithm/count and refresh API are unspecified. Config supplies ordered daily/weekly template pools and selected counts; deterministic circular selection avoids runtime random seeds. Empty pools/count zero are valid. Refresh is explicit for UI reads and automatic for events/claims; no timer/background worker.
- Weekly hook semantics/claim namespace are unspecified. Weekly templates form a second list in the same module and section; they consume matching events, retain state through the week, reset on UTC Monday, and use `quest:<mondayDate>:<questId>`. No callback event is added.
- Zero event increments are valid no-ops for progress and can refresh the period. Unknown nonempty event keys affect no progress. Positive int targets are required. Unknown quest IDs return NotFound without resetting state.
- Arithmetic overflow is rejected before capping, including when progress is already complete. Since the event parameter is long but progress is int, any event amount greater than int.MaxValue is rejected; typed reward fields cannot represent values above their long/int limits, and overflowing persisted integers are rejected by section conversion.
- Unsupported module section versions, config-incompatible saved selections, and malformed section fields fall back to defaults with CorruptSection; no module migration is invented. Missing/null sections follow SaveDocument's successful default behavior.
- AlreadyClaimed from the grantor reconciles the local flag/slot and returns AlreadyClaimed. Rejected grants leave claims retryable. Durable cross-module atomicity belongs to the host SaveStore orchestration and the grantor's persisted claim ledger; these modules do not invent a transaction layer. A host must persist the modules and grantor together for restart-safe duplicate protection.
- Services are intended for serialized calls by the host. Thread synchronization, reentrant grantors, and arbitrary dependency exceptions are outside this task. IClock.UtcNow is treated as UTC according to its contract.
